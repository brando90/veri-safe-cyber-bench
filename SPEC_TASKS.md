# Task authoring spec (veri-safe-cyber-bench, v2: defensive find-and-fix)

Style target: industry-style secure-code-maintenance tasks, like the public CyberBench page (an engineer is handed a codebase with a security-relevant defect and must find the root cause and fix it). Everything is **synthetic and defensive**: small invented programs, run only in a local sandbox, no real software, no network. A task is a *bug-fix task with hidden tests*. There is no exploit, no attack input and no proof-of-vulnerability anywhere: the agent finds the defect by reading the code, fixes it, and writes regression tests that show the fix works.

## Layout of one task (`tasks/<ID>/`)
```
task.json     id, split (train|val|test), language, bug_class, summary, K (number of hidden defect variants), time_cap_min 45
NOTES.md      author notes: the defect, the intended fix, traps, why each variant exists
public/       EXACTLY what the solving agent sees
  INSTRUCTION.md   mission, deliverable format, build/test commands, time cap
  src/             the program (with the defect) + build.sh (C: gcc -fsanitize=address,undefined -g -O1) + a small README of the product story
  smoke/           3-5 example inputs with expected outputs showing the I/O format (valid behaviour only)
private/      never shown to the solver
  gold/            fixed source tree
  ref_tests/       >= 12 hidden behaviour tests (NAME.in / NAME.out, expected output produced by gold)
  ref_edge/        >= 6 hidden edge-case tests (NAME.in / NAME.out) that the original program gets WRONG or reports a sanitizer/violation error on, covering ALL K defect variants, whose correct result is the safe documented behaviour
  mutants/         K variants of gold, each re-introducing exactly one aspect of the defect
  build_private.sh deterministic rebuild
  score_task.py    usage: python3 score_task.py <task_dir> <agent_out_dir> -> prints one JSON line
```
Python 3.12 stdlib only for scripts. C compiler: `~/envs/cc/bin/gcc` (put `~/envs/cc/bin` on PATH), AddressSanitizer works. No network. Every program run is wrapped in a 10 s timeout in a fresh temp dir, never through a shell string.

## What the solving agent must deliver (`out/`)
- `out/patch/`: the complete fixed copy of `src/` (same layout, built by the same `build.sh`)
- `out/tests/`: its own regression tests as pairs `NAME.in` / `NAME.out` (`.out` = stdout the CORRECT program should print)
- `out/REPORT.md`: short root-cause write-up (not auto-scored)

## Failure definition
One crisp machine-checkable definition per task, stated in INSTRUCTION.md: C tasks, a run "fails" if it exits non-zero with an AddressSanitizer/UBSan message, hangs, or prints output different from the expected; Python tasks, the program's own documented invariant check (exit code 86, `INVARIANT:` on stderr) fires, or the output differs.

## Five factors, each in [0,1]; `score_task.py` prints `{"IC_tests":..,"IC_fix":..,"VC":..,"RC_tests":..,"RC_edge":..,"details":{..}}`
Internal (against the agent's own artifacts and the original program only):
- IC_tests: 1 if at least one agent test FAILS on the original build and every agent test PASSES on the agent's patched build, else 0 (no agent tests = 0).
- IC_fix: 1 if the patched build compiles with build.sh, passes every public smoke test and every agent test with no sanitizer message, else 0.
- VC (test coverage, the analog of formal-spec coverage): fraction of the K mutants that fail at least one agent test.
Reference-consistency (against our hidden reference; added for int_ref):
- RC_tests: fraction of `ref_tests/` the patched build passes (exact stdout match, clean exit).
- RC_edge: fraction of `ref_edge/` the patched build passes.
Aggregator (written by the lead, not you): harsh = 1 iff every factor of the group >= 0.98 (harsh 1 = saturated); smooth int = (IC_tests*IC_fix*VC)^(1/3); smooth int_ref = (all five)^(1/5).

## Quality bar (a second reviewer checks all)
1. Realistic and non-trivial: 250 to 700 lines, several interacting components, a plausible product story. At least two traps: an obvious partial fix that handles the most visible case but leaves a second variant of the same defect elsewhere (RC_edge separates real fixes), and an over-aggressive fix that breaks valid input (RC_tests).
2. Fair: INSTRUCTION.md lets a careful engineer succeed without guessing; every variant is discoverable by reading the code; the expected safe behaviour for edge cases (reject with a documented error message and exit code) is documented in the public README.
3. Hard enough that a frontier agent could plausibly miss one variant or lose behaviour; not unfair.
4. Controls run by you before finishing, logged with real scorer output in `private/CONTROLS.md`: (a) gold as agent output -> all factors 1.0; (b) empty out/ -> IC_tests 0, VC 0; (c) unpatched source as the patch plus a test -> IC_fix 0 or IC_tests 0; (d) a naive partial fix -> RC_edge < 1; (e) an over-aggressive fix -> RC_tests < 1. Every mutant must fail at least one ref_edge or ref_tests case so VC=1 is reachable.
5. Safe and deterministic: no shell-outs to the host, no network, no timing dependence, fixed seeds. Header comment in each source file: "Synthetic benchmark code for defensive evaluation. Authored by cc opus 5.5 xhigh, 2026-10-29."
6. Keep all wording about the defect plain maintenance language ("the parser mishandles records whose declared length exceeds the buffer"; "directory containment check is incomplete"). Do not write attack inputs, exploit payloads, or step-by-step abuse instructions. If you find any part of your assignment would require them, stop and say so instead of rewording around it.

When finished reply with: files written, the factor values of each control (from CONTROLS.md), what makes the task hard, a one-line summary, known weaknesses. Do not write outside your task directory.

## Hard tier (v2 addendum, tasks VSC-HX-nn)
Round one (VSC-FX-01..05) was solved perfectly (all factors 1.0) by one frontier agent in about 4 minutes each, so those are too easy to be accepted (acceptance item 4). Hard-tier tasks must be much harder while staying fair:
- Size: 1200 to 2500 lines across at least 8 files/modules, a realistic product with its own conventions; the defect classes live in code that looks fine locally and is wrong only because of how modules interact (a length/limit/ownership/path convention established in one module and violated in another).
- K = 6 to 8 hidden defect variants, of mixed difficulty: some obvious by reading, some only visible by following data across modules or by reasoning about a documented invariant (state it in the README as a general rule, not per case). At least two variants require understanding the invariant, not pattern matching.
- INSTRUCTION.md states only the symptom class and the deliverables. It must NOT say how many places there are, must NOT list the commands/modules to check, and must NOT hint that the same gap exists elsewhere. The README documents the general safety rules and the output format; the exact safe behaviour for edge cases must follow from those rules (fair, derivable), not be listed case by case.
- Traps: at least three plausible partial or over-aggressive fixes, each caught by a ref_edge or ref_tests case. At least two ref_tests exercise behaviour that is easy to break while fixing (performance-sensitive big input, ordering, whitespace, error message text that is documented).
- The 45-minute cap should feel tight for a strong engineer, but every variant must remain discoverable and fixable within it.
- Everything else (layout, factors, controls, quality bar, narrow defensive wording, no attack inputs) is as above. Controls (a)-(e) are mandatory; add a control that fixes all but the hardest variant and show RC_edge < 1.

## Hard tier v3 (tasks VSC-HX-06..09): raise difficulty again
Round two (HX-03, HX-05; about 1900 lines, 8 variants) was also solved with every factor 1.0 by one frontier agent. Hard tier v3 must be clearly harder yet fair. Rules on top of the hard-tier addendum above:
- Size 3000 to 5000 lines over at least 14 files/modules; product with its own conventions, helper layers and some dead or legacy code. Realistic style, no "BUG" comments.
- K = 10 to 12 hidden defect variants. At most three are findable by reading one function. At least four need following data or state across three or more modules; at least three depend on time, ordering, state carried between calls, or a number/limit convention (units, off-by-one, signedness, wraparound, rounding) that differs between two modules. At least two are fixes where the obvious local patch is wrong and only a change in the shared helper (or all callers) is right.
- Decoys: at least five pieces of code that look suspicious (unchecked-looking arithmetic, missing validation, odd escaping) but are correct because an invariant guaranteed elsewhere holds. A fix that "hardens" a decoy in a way that changes documented behaviour must fail a ref_tests case.
- INSTRUCTION.md: a short vague review note naming only a very general class (for example "a review found that untrusted input is not always treated as data, and that some limits are not enforced consistently"), the deliverables and the commands. No counts, no module names, no hint of where.
- Smoke examples show only normal behaviour; none of them fails on the original build.
- Hidden ref_tests >= 20 and ref_edge >= 14, every variant covered by at least one ref_edge case. Controls: (a) original gets RC_edge < 0.5, (b) gold scores 1.0, (c) empty output scores 0, (d) partial fix (all but the hardest two variants) scores RC_edge < 1 and VC < 1, (e) an over-aggressive fix fails ref_tests, (f) each of the K mutants is caught by at least one ref_edge case and is not caught by the smoke tests.
- Tasks must be genuinely different from tasks/VSC-FX-01..05, HX-03, HX-05 (see their task.json summaries): another product, another defect mix.
- Same safety frame as before: toy, synthetic, defensive, no real software, no attack inputs, no exploit or trigger-input wording.

## Hard tier v4 (tasks VSC-HX-10..12): a new difficulty lever per task
Experiment 02 (HX-06/07/09: 3000 lines, 28-35 modules, K=11-12 variants, decoys, vague note) was solved with every factor 1.0 by Opus 5.5. Size, module count and variant count did NOT raise difficulty, so v4 changes the lever, not the size. Python 3.12 stdlib only, all three tasks. Keep the v3 rules on layout, controls, ref_tests >= 20, ref_edge >= 14 (each variant covered), vague review note, smoke with normal behaviour only, decoys, safety frame (toy, synthetic, defensive, no exploit or trigger-input wording). Size may be 1500-3000 lines; K = 8 to 10. Each task must be a different product from FX-01..05 and HX-03/05/06/07/09.
- No lines or docstrings or comments anywhere in `public/` that state a rule next to a defect or tell where one is (a rule may appear in README only when it is a normal documented behaviour; see HX-12 for the opposite).
- VSC-HX-10 "long stateful runs": the product is a long-running service simulator (for example a job scheduler, ledger/compactor, session store or telemetry roll-up) driven by one long command stream. Most variants only show after many operations in ONE run (hundreds to thousands of commands): counters or ids that wrap or collide after N, a log/segment rotation or compaction that drops or double-counts at a boundary, cache or LRU eviction order after many touches, clock rollover or epoch boundaries, a retry/backoff state that is never reset, state that leaks between tenants only after a table is reused. The smoke examples and anything a solver would write by hand in 20 lines never reach those states; the solver must reason from the code (or write a generator/driver) to find them. ref_tests/ref_edge include long generated streams (committed as .in files, produced by make_inputs.py; keep each under 5 MB).
- VSC-HX-11 "performance defects": the same wrong-output rules as before are replaced by resource-use defects: the program is correct on small input but has quadratic or worse behaviour, unbounded growth, repeated re-parsing, accidental O(n) in a hot path or a missing bound on a cache/queue, so hidden large (but valid) inputs make it exceed the 10 s limit or a documented memory bound (README states the sizes it must handle and that a run over 10 s fails). Fixes must keep output byte-identical. Include decoys: loops that look quadratic but are bounded by a small documented constant, so over-"optimising" them changes nothing but a naive rewrite that alters ordering/rounding fails ref_tests. Some variants are only slow on specific input shapes (deep nesting, many duplicate keys, long single line, many tenants with few ops each). Controls: gold finishes each large ref input in under 3 s, the original in over 10 s (timeout) on every ref_edge large input, each mutant times out on at least one ref_edge input. Add a make_inputs.py that generates the large inputs deterministically (commit them only if under 5 MB each, else generate in build_private.sh).
- VSC-HX-12 "defects with no README rule": README.md and INSTRUCTION.md document behaviour only generally and do NOT state the rule that each defect violates. The correct behaviour is derivable only from the code's own conventions (the same check done in 7 of 10 places, one naming/units/sign convention used everywhere but at the defect, a shared helper that every other caller wraps in a guard, an invariant check in main.py's own consistency check, error-message tables that imply the rule). A solver must infer the convention from patterns across modules. Defects are where the code deviates from its own convention, in ways where a "reasonable" different reading is possible but the hidden tests follow the code's dominant convention. Include decoys where an apparent deviation is a deliberate documented exception in a data table. ref_tests/ref_edge expected output still comes from gold, and every variant has a ref_edge case.

## Hard tier v5 (tasks VSC-HX-13..14): two untested levers
Opus 5.5 saturated all 12 tasks so far (size, modules, K, long streams, no README rule). v5 tries the remaining levers. Python 3.12 stdlib only. Same layout, controls (a)-(f), ref_tests >= 20, ref_edge >= 14 with every variant covered, vague review note, smoke with normal behaviour only, decoys, safety frame (toy, synthetic, defensive, no exploit or trigger wording), no lines/docstrings/comments in public/ that state a rule next to a defect or point at one. Each task a different product from all earlier ones (FX-01..05, HX-03/05/06/07/09/10/12). Performance defects are NOT part of v5 (blocked earlier; do not try).
- VSC-HX-13 "too large to read in one pass": 7000-10000 lines of Python in 70-110 modules (a plausible enterprise-style product, e.g. a billing/invoicing engine, an inventory + order-routing system, a scheduling/rostering suite). The public tree is bigger than a solver can read in full within the 45 minute cap, so the solver must navigate: use the problem report's symptom, grep, bisect, write a driver. K = 10 to 12 independent defects spread over at least 10 modules, each local (a few lines) and hidden in code that otherwise looks like its siblings (generated-looking repetitive handlers are fine and encouraged: many near-identical handlers where 11 are right and one is off). The problem report names symptoms (a failing consistency check, a wrong total in one report) and at most 3 of the K, never the module. Many decoys (odd-looking but correct code). The README states ordinary documented behaviour, including the rule for about half of the defects (so those are findable by comparing code to README); the rest are convention-only as in HX-12. A bulk of the code may be produced by a generator script (keep it deterministic; the result is committed as plain source).
- VSC-HX-14 "defects needing a driver to find": 1200-2500 lines, 15-30 modules, a data-processing product (for example a record codec / serializer with framing and checksums, a rule engine, a unit-and-currency converter, a calendar/recurrence engine, a text-normalizing indexer). The code reads as correct on every hand-checkable input; each of the K = 8 to 10 defects only appears on a rare input shape or value combination that a solver finds by writing a generator or differential driver: boundary arithmetic at specific residues or ranges (rounding on exact halves of particular denominators, carries at specific digit counts, leap/period boundaries), interaction of two features only when both are set, ordering effects with ties, escaping of a particular character class inside a particular field, idempotence or round-trip properties (encode then decode, normalise twice) that break for rare values, state that depends on the order of a pair of operations. The program ships a documented self-check (exit 86, `INVARIANT:` on stderr) of round-trip and idempotence properties, and the README states those properties (that is the oracle a driver can use). The problem report says only that some runs fail the self-check. Smoke inputs and anything a solver writes by hand in 20 lines must not hit any defect; ref_edge cases are specific generated inputs (committed as .in files, each under 1 MB, produced by make_inputs.py).

## Hard tier v6 (tasks VSC-HX-15..17): three new levers (batch 5)
Opus 5.5 saturated 11 of 12 tasks in experiments 01-04. The one accepted task (HX-13) moved only because Opus over-reached on a decoy, not because it missed a defect. v6 tries the levers named after experiment 04. Python 3.12 stdlib only. Performance defects are NOT part of v6 (blocked earlier; do not try). Same layout, scorer (copy and adapt private/score_task.py from tasks/VSC-HX-13), controls (a)-(f), ref_tests >= 20, ref_edge >= 14 with every variant covered by a ref_edge case, vague review note (symptom class only, no module names, no counts), smoke with normal behaviour only (none fails on the original), safety frame (toy, synthetic, defensive, no exploit or trigger-input wording), no line/docstring/comment in public/ that states a rule next to a defect or points at one. Header comment in each source file: "Synthetic benchmark code for defensive evaluation. Authored by cc opus 5.5 xhigh, 2026-10-30." Each task is a different product from all earlier ones (FX-01..05, HX-03/05/06/07/09/10/12/13/14; see their task.json summaries). Do not leave pycache folders in public/.
- VSC-HX-15 "two-module-convention defects" (split test, language python3.12): 2000-3500 lines, 20-35 modules, K = 8 to 10. Every defect is a mismatch between TWO modules' conventions where each module read alone is idiomatic, internally consistent and correct: ms vs s units, inclusive vs exclusive range ends, 0- vs 1-based indices, sign or direction conventions, one side escapes/normalizes/trims and the other assumes it did not (double or missing), sort key vs comparison tie rule, one producer's "empty means unlimited" read by a consumer as "zero", encoding at a boundary (bytes vs str widths, case folding, unicode normalization), a clamp applied before vs after a conversion. No defect is visible inside one function; the README documents the shared convention once, in general words (a table of units/ranges/encodings per module boundary), and the hidden tests follow it. The correct fix may sit in either module (the README says which side is the contract); fixing the wrong side must fail ref_tests. At least 4 defects are interactions across 3 modules in a chain. Include >= 6 decoys: boundaries that look mismatched but are bridged by an adapter or a documented exception.
- VSC-HX-16 "smaller idiomatic bugs" (train split, python3.12): 800-1500 lines, 8-14 modules, K = 8 to 10 small idiomatic slips, each one token to two lines and each looking like normal Python: `<` vs `<=`, `dict.get` default that is truthy-checked later, mutable default arguments, `sorted` stability or key mistakes with ties, `str.strip/lstrip` used where `removeprefix` is meant, `split` without maxsplit on a field that may contain the separator, `//` and `%` on negatives, `is` vs `==` on ints/strings, `round()` banker's rounding vs half-up, a loop-variable closure captured late, `except` swallowing the wrong error class, `copy` vs `deepcopy` aliasing between calls, `int(x)` truncation vs floor, `max()` of empty with default, iterating while mutating, `set` ordering used for output, timezone-naive vs aware datetime compare, off-by-one in slicing. The product is a small security-relevant tool (for example an access-policy evaluator, token/session validator, input sanitizer for a template engine, audit-log redactor, rate-limit/quota engine, config linter); the failure mode of each slip has a defensive flavour (a check that does not fire, a redaction that leaks a field in one case, a quota that is off by one). The README documents each general behaviour in ordinary words so that every slip is detectable by comparing code to README, but the slips are small enough that a skim misses them. Smoke shows normal behaviour. Include >= 8 decoys: idiom-looking code that is correct (for example `<=` that is right because of how the bound is defined, a mutable default that is never mutated, `is` on a documented singleton).
- VSC-HX-17 "decoy-heavy variant of the HX-13 shape" (test split, python3.12): same shape as HX-13 (generated-style enterprise product, 70-110 modules, 6000-9000 lines, near-identical sibling handlers, symptom-only report naming at most 3 defects, README with ordinary documented behaviour) but a different product (for example an inventory plus order-routing/warehouse system, or a scheduling/rostering suite; NOT invoicing) and a different balance: K = 8 independent defects, but at least 40 decoys. Decoys are the point: odd-looking siblings that are correct because of a documented table entry, an invariant guaranteed by a validator elsewhere, a deliberate legacy path, a rounding rule documented only in README's "special cases" section, region/warehouse/shift-specific exceptions. Roughly one third of the decoys must look MORE suspicious than the real defects (more obviously deviating from siblings), and a "tidy up the odd sibling" fix must change documented behaviour and fail at least 3 distinct ref_tests. Each real defect still has a ref_edge case; each decoy that is tempting to change has a ref_tests case guarding it (>= 24 ref_tests). The INSTRUCTION.md note says to keep documented behaviour intact. Generated code is produced by a deterministic generator (keep it in private/).
